# 搭手更新边界

从 `0.1.3-rc.14` 开始，客户端只运行安装包内置的前端页面。旧版本下载过的 UI 和文案缓存会在启动时自动清理。

## 当前发布方式

| 变化内容 | 当前方式 |
|---|---|
| 修改文字、HTML、CSS 或前端 JavaScript | 随下一版 DMG / EXE 发布 |
| 修改 Rust、系统权限、本地服务或随包程序 | 随下一版 DMG / EXE 发布 |

暂时多下载一次安装包，会比在高权限主窗口中自动运行可替换 JavaScript 更稳妥。客户端仍使用 Tauri 原生更新器检查和安装完整更新，并展示版本号和更新说明。

## 为什么暂停小包更新

旧方案让 UI 小包与原生安装包共用一把签名密钥，而且下载后的 JavaScript 会进入拥有本地命令能力的主窗口。即使文件签名和 CSP 都通过，这个权限边界仍然过大。

因此 rc.14 做了三件事：

- 停止下载和启用远程 UI/文案包；
- 移除内容发布工作流，不再把原生更新私钥交给前端构建任务；
- 保留旧 Bridge 命令的无操作兼容返回，避免旧页面或回滚流程直接崩溃。

## 未来如何恢复增量文字更新

文字更新仍值得做，但恢复前必须同时满足：

- 使用与原生更新完全独立的内容签名密钥；
- 只允许类型化、长度受限、不能包含 HTML 的纯文字目录；
- 签名内容同时绑定版本、兼容范围、哈希和有效期；
- 客户端失败后自动回到内置文案；
- 下载内容不能获得新的 Tauri 权限。

可执行的 HTML、CSS 和 JavaScript 不再计划进入高权限主窗口的小包更新通道。若未来确有必要，应放入单独的低权限 WebView，并经过新的安全评审。
